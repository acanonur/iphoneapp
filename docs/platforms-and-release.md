# What this project is, and how to release it

## 1. What kind of project is KnitStudio?

It is a **native Swift application built with SwiftUI**, with no backend and no
third-party dependencies.

| | |
|---|---|
| Language | Swift 5.9 |
| UI framework | SwiftUI (declarative, Apple's current UI toolkit) |
| Minimum OS | iOS 17, macOS 14 |
| Project file | Generated by [XcodeGen](https://github.com/yonaskolb/XcodeGen) from `project.yml` |
| Tests | XCTest (`⌘U` in Xcode) |
| Dependencies | **None.** No CocoaPods, no Swift Package Manager, no npm |
| Network | **None.** Everything runs on-device |
| Storage | One JSON file in Application Support |

### Why there is no `.xcodeproj` in git

`.xcodeproj` files are large, machine-generated, and conflict badly in git.
Instead the project is described in `project.yml` (83 lines you can actually
read) and XcodeGen builds the Xcode project from it:

```bash
brew install xcodegen
cd ios-knitstudio
xcodegen generate          # creates KnitStudio.xcodeproj
open KnitStudio.xcodeproj
```

Run that again any time you add a file — sources are picked up by folder, so
you never edit project settings by hand.

### How the code is layered

```
KnitStudio/
  Engine/      pure Foundation. Gauge, shaping, yarn model, one file per
               calculator. No UI imports at all — this is the valuable part.
  Content/     the technique guide, abbreviations, presets, built-in charts.
  Import/      image → chart, written-pattern parser, file loading.
  Platform/    the ONLY file that knows about iOS vs macOS differences.
  Views/       SwiftUI screens.
  App/         entry point, store, persistence.
KnitStudioTests/   engine, calculators, charts, parser, shopping list.
```

That `Engine` layer having no UI imports is not decoration — it is what made
the Mac version cheap, and it is what would make an Android port tractable.

### How this differs from the other app in the repo

`ios/` + `backend/` is **AI Secretary**: a SwiftUI client that talks to a
Node/Fastify server, which in turn calls a telephony provider. It needs a
server running. KnitStudio needs nothing but the device.

## 2. Where this code can and cannot run

| Platform | Status | How |
|---|---|---|
| **iPhone / iPad** | ✅ Works | Native SwiftUI |
| **Mac** | ✅ Works | Native SwiftUI (not Mac Catalyst) — sidebar layout, resizable window |
| **Apple Vision Pro** | ⚠️ Would probably run | Add `visionOS` to `supportedDestinations` and test |
| **Android** | ❌ **Cannot run** | Swift and SwiftUI do not exist on Android. See section 5 |

This is worth being blunt about: **there is no setting, flag, or build option
that makes this codebase produce an Android app.** SwiftUI is Apple-only.
Android needs either a transpiler or a rewrite. Section 5 lays out the options
honestly, with effort estimates.

## 3. Releasing on iOS and iPadOS

### What you need first

1. **A Mac.** iOS apps can only be built and signed on macOS. There is no way
   around this.
2. **Xcode 15 or newer**, free from the Mac App Store.
3. **Apple Developer Program membership — $99 per year.** Required to put an
   app on the App Store. Without it you can still install on your own device
   for 7 days at a time, which is fine for trying it out.

### Step by step

**1. Pick a real bundle identifier.**
The project currently uses the placeholder `com.example.knitstudio`. Change it
in `project.yml` to something you own, in reverse-domain form:

```yaml
PRODUCT_BUNDLE_IDENTIFIER: com.yourname.knitstudio
```

Then re-run `xcodegen generate`. This identifier is permanent once you ship —
you cannot change it later without shipping a different app.

**2. Register the App ID and enable signing.**
In Xcode: select the KnitStudio target → *Signing & Capabilities* → tick
*Automatically manage signing* and pick your team. Xcode registers the App ID
with Apple for you.

**3. Add an app icon.**
`KnitStudio/Assets.xcassets/AppIcon.appiconset/` is set up and waiting. Drop a
**1024×1024 PNG with no transparency and no rounded corners** into the iOS
slot in Xcode's asset editor. Apple rejects submissions with a missing or
transparent icon — this is the single most common avoidable rejection.

**4. Create the app record in App Store Connect.**
At [appstoreconnect.apple.com](https://appstoreconnect.apple.com) → *My Apps* →
*+* → *New App*. You need:
- the bundle ID from step 1,
- an app name (30 characters, must be unique across the whole App Store),
- a primary language, and an SKU (any private string, e.g. `knitstudio-001`).

**5. Fill in the store listing.**
- **Description** and a **promotional subtitle**.
- **Keywords** (100 characters, comma-separated, no spaces after commas).
- **Screenshots.** Required: 6.7" iPhone. If you support iPad — this app does —
  you also need 13" iPad screenshots. Take them in the Simulator with
  `⌘S`, which saves at the exact required pixel size.
- **Support URL** and **privacy policy URL**. Both are mandatory. A single
  static page is fine.
- **Age rating** questionnaire. For this app everything is "None".

**6. Fill in the privacy details ("nutrition label").**
For KnitStudio the honest answers are straightforward: **no data collected, no
tracking**. `KnitStudio/PrivacyInfo.xcprivacy` already declares this in the
bundle, and it should match what you tick in App Store Connect. Nothing leaves
the device, so answer *"No, we do not collect data from this app."*

**7. Archive and upload.**
In Xcode, set the run destination to *Any iOS Device (arm64)* — you cannot
archive against a simulator — then *Product → Archive*. When the Organizer
opens: *Distribute App → App Store Connect → Upload*.

**8. TestFlight.**
The build appears in TestFlight after processing (usually 5–30 minutes). Test
it on a real device before submitting. Internal testers (up to 100 people on
your team) need no review. External testers (up to 10,000) need a short first
review, usually a day.

**9. Submit for review.**
In App Store Connect, attach the build to your version and *Submit for Review*.
Review typically takes **24–48 hours**. If rejected, you get a message in the
Resolution Center; fix and resubmit, which usually re-reviews faster.

### Things that specifically matter for this app

- The app writes to Application Support and reads files the user picks. Nothing
  requires a special capability.
- `NSPhotoLibraryUsageDescription` is already set — Apple rejects apps that
  show a system permission prompt without an explanatory string.
- No account, no login, no network, so there is no "demo account" to supply and
  the sign-in review guidelines do not apply.
- Apple periodically raises the **minimum SDK** new submissions must be built
  with. Building with the current Xcode release keeps you compliant.

## 4. Releasing on macOS

Same Apple Developer account, and you have two quite different options.

### Option A — Mac App Store

Same flow as iOS: archive with the Mac destination, *Distribute App → App Store
Connect*. The App Sandbox is mandatory, and it is already configured in
`project.yml`:

```yaml
com.apple.security.app-sandbox: true
com.apple.security.files.user-selected.read-only: true
```

Those two are all this app needs — no network entitlement, because it makes no
network calls. Mac screenshots are required in addition to the iOS ones.

### Option B — Distribute it yourself (a `.dmg` from your own site)

No App Store, no 15–30% commission, no review. But you must:

1. **Sign** with a *Developer ID Application* certificate (not the App Store one).
2. **Notarize**: upload the build to Apple's automated malware scan.
   ```bash
   xcrun notarytool submit KnitStudio.dmg \
     --apple-id you@example.com --team-id YOURTEAMID --wait
   xcrun stapler staple KnitStudio.dmg
   ```
3. Ship the stapled `.dmg`.

Skip notarization and Gatekeeper will tell your users the app is damaged.
`ENABLE_HARDENED_RUNTIME: YES` is already set, which notarization requires.

**Which to choose?** The Mac App Store gets you discovery and handles updates.
Direct distribution gets you a faster release cycle and the full price. For a
companion to an iOS app, the Mac App Store is usually the easier answer — and
you can offer it as a *universal purchase* so buying the iPhone app includes
the Mac app.

## 5. Android: what it would actually take

### Why the current code cannot be reused directly

Android runs Kotlin and Java on the ART runtime, with Jetpack Compose or XML
layouts for UI. Swift has no official Android toolchain, and SwiftUI is closed
Apple technology that will never run there. The parts of KnitStudio that touch
Apple frameworks — SwiftUI views, Core Graphics image sampling, PDFKit,
PhotosUI — have no Android equivalent that Swift could call.

### What *is* portable

This is the good news, and it is a large fraction of the value:

| Layer | Lines | Portability |
|---|---|---|
| `Engine/` | ~2,000 | **Pure logic.** Arithmetic, structs, enums. Ports almost mechanically |
| `Content/` | ~1,300 | **Pure data.** Technique text, presets, charts. Ports as data |
| `Import/` parser | ~400 | **Pure logic**, only regex. Ports directly |
| `Import/` image | ~250 | Needs an Android bitmap API, but the algorithm is unchanged |
| `Views/` | ~2,500 | Rewrite in Compose |
| `KnitStudioTests/` | ~900 | **These are a specification.** Port them and you know the port is right |

The test suite is the thing that makes this tractable: every calculator has
verified expected values, so a Kotlin port is correct exactly when the same
tests pass.

### The four realistic options

**A. Skip ([skip.tools](https://skip.tools)) — transpile SwiftUI to Compose.**
A commercial tool that compiles Swift to Kotlin and SwiftUI to Jetpack Compose.
You keep one Swift codebase. Needs a Mac and Android Studio, has a paid licence
for closed-source apps, and constrains you to the SwiftUI subset it supports.
*Effort: days to weeks. Risk: you inherit someone else's compatibility matrix.*

**B. Port the engine to Kotlin, write a Compose UI. ← my recommendation**
Keep the Apple apps exactly as they are. Translate `Engine/`, `Content/` and the
parser to Kotlin (they are plain logic — no framework calls), port the XCTest
suite to JUnit to prove the translation, then build an Android UI in Compose.
*Effort: roughly 2–4 weeks for one developer. Risk: low — the maths is already
specified and verified. Cost: two UI codebases to maintain.*

**C. Kotlin Multiplatform / Compose Multiplatform.**
Write the engine once in Kotlin, share it across Android, iOS and desktop, and
write the UI once in Compose Multiplatform. The cleanest long-term three-platform
story — but it means discarding the SwiftUI work and accepting a non-native feel
on iOS.
*Effort: 4–8 weeks. Best if Android is a first-class platform, not an afterthought.*

**D. Rewrite in Flutter or React Native.**
One Dart or TypeScript codebase for iOS, Android and (with Flutter) macOS.
Throws away everything here.
*Effort: 6–10 weeks. Only worth it if you were going to start over anyway.*

### If Android matters most, decide now

The honest trade-off: **B** preserves the polished native Apple apps you already
have and gets Android with low risk, at the cost of maintaining two UIs.
**C** gives you one UI everywhere but means the iOS app stops being native
SwiftUI. There is no option that gets all three platforms from this exact code.

Tell me which direction you want and I can start it — porting the engine to
Kotlin with the tests is a well-defined first step that is useful under both
**B** and **C**.

## 6. Releasing on Google Play (for when there is an Android build)

Worth knowing in advance, because one requirement catches people out.

1. **Google Play Developer account — $25, one time** (versus Apple's $99/year).
2. **Build an Android App Bundle (`.aab`)**, not an APK. Play requires AAB for
   new apps.
3. **Signing.** Use *Play App Signing*: you upload with an upload key, Google
   holds the real signing key. If you lose your upload key it can be reset; lose
   a self-managed signing key and you can never update the app again.
4. **⚠️ The 12-tester rule.** New **personal** developer accounts must run a
   closed test with **at least 12 testers who stay opted in for 14 continuous
   days** before they can apply for production access. Organisation accounts are
   exempt. This routinely adds two or more weeks to a first launch — start it
   early. (Business-entity accounts also require identity verification.)
5. **Target API level.** Play enforces a minimum `targetSdk` for new and updated
   apps, raised every August. Check the current requirement in the Play Console
   before you build — this changes yearly and lags behind whatever a tutorial
   tells you.
6. **Store listing**: title (30 chars), short description (80), full description
   (4,000), a 512×512 icon, a 1024×500 feature graphic, and screenshots.
7. **Data safety form** — Play's equivalent of Apple's privacy label. For this
   app: no data collected, no data shared.
8. **Content rating** questionnaire, via the IARC.
9. **Review** typically takes hours to a few days, and is usually less strict
   than Apple's — but first-time submissions from new accounts are slower.

### The main practical differences from the App Store

| | App Store | Google Play |
|---|---|---|
| Cost | $99/year | $25 once |
| Build machine | Mac required | Any OS |
| Review | 24–48h, strict | Hours–days, lighter |
| First release | Straight to review | 12 testers × 14 days first (personal accounts) |
| Staged rollout | Phased release | Percentage rollout, halt and resume |
